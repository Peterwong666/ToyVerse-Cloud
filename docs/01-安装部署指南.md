# 安装部署指南

> **适用对象**：需要在本机跑通本项目、或把本项目部署到服务器的工程人员
> **前置条件**：本地方式需 Python 3.12+；Docker 方式需 Docker 与 Docker Compose。**不需要 Node.js**（前端为零构建 ES Module）
> **配套文档**：[`02-系统流程图.md`](./02-系统流程图.md)（业务怎么流转）、[`03-系统架构图.md`](./03-系统架构图.md)（分层与部署拓扑）、[`../SECURITY.md`](../SECURITY.md)（安全设计与已知安全边界）
> **最后更新**：2026-09-17
> **文档中标注说明**：✅ = 已实测（含命令与输出）；⚠️ = 未验证 / 需你自己确认

## 0. 结论先行

### 0.1 三条路径，选一条

| 你的目的 | 用哪条 | 命令 | 耗时 |
|---|---|---|---|
| 跑起来看看 / 改代码 | 本地开发 | `make setup` → 改 `.env` 强密码 → `make dev` | 3–5 分钟 |
| 验证部署形态 / 给他人演示 | Docker（SQLite） | `make up` | 5–10 分钟（首次含构建） |
| 接近生产的形态 | Docker + Nginx | `make up-nginx` | 同上 |

✅ **两条路径都实测通过**：容器构建成功并进入 `healthy`；`make smoke` **57/57**（直连与经 Nginx 各一次）；
`down && up` 后数据**完全一致**（租户 2 / 设备 11 / 订单 2 / 工厂工单 0）。

### 0.2 ★ 动手前必须知道的三个坑

| # | 坑 | 后果 | 怎么办 |
|---|---|---|---|
| 1 | **本项目不预置任何默认口令**。`.env` 里三个 `*_ADMIN_PASSWORD` 为空或过弱 | 服务**拒绝启动**并退出（不是警告） | 复制 `.env.example` 后立刻设置强密码；生成方式见 `## 2.2` |
| 2 | **不要把开发机的 `.env` 直接搬进容器**。开发用 `DATABASE_URL` 是**相对路径** | SQLite 文件落进镜像层而非挂载卷，容器重建即丢数据 | 容器用**独立的** `APP_DATABASE_URL`（compose 已设好默认值），见 `## 3.5` |
| 3 | 容器里跑 **4 个 uvicorn worker**，而 SQLite 写并发能力有限 | 演示与轻负载无问题；真实多租户并发写会锁等待 | 需要并发写就切 PostgreSQL（`--profile postgres`），见 `## 3.4` |

> **为什么把这三条放在最前面**：它们都属于「本地看起来正常、一换环境就出事」的类型。
> 第 2 条尤其隐蔽——容器里也能写文件，只有**重建容器**时才暴露丢数据。
> 这个坑是本项目在部署验收时实测踩到的（详见 `## 7.1`）。

| 项 | 要求 | 说明 |

## 2. 本地三步跑通

### 2.1 第一步：拿到代码

```bash
git clone <repo-url>
cd saas_ai_toy_platform
```

### 2.2 第二步：★ 设置强密码（不可跳过）

```bash
cp .env.example .env
```

然后编辑 `.env`，**至少**填这三个（其余可留默认）：

```ini
PLATFORM_ADMIN_PASSWORD=<强密码>
MERCHANT_ADMIN_PASSWORD=<强密码>
FACTORY_ADMIN_PASSWORD=<强密码>
```

生成一个够强的随机值：

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

> ⚠️ **为什么不能省**：`app/core/config.py` 的 `validate_security()` 在启动时会校验这些口令。
> 为空、长度不足 `MIN_PASSWORD_LENGTH`（默认 8）、或命中常见弱口令（`admin` / `password` /
> `12345678` / `admin@2024`）时，服务**抛 `InsecureConfigurationError` 并拒绝启动**。
> 完整拒绝条件清单见 `## 5.`。

同样建议显式替换 `.env.example` 里这两个**占位密钥**（它们在默认值里带 `dev-only-insecure` 标记，
启动期会因含弱标记而被拒）：

```ini
JWT_SECRET_KEY=<另一段随机值，至少 32 字节>
QR_SIGN_SECRET=<另一段随机值，至少 16 字节>
```

### 2.3 第三步：初始化并启动

```bash
make setup    # 创建虚拟环境 + 安装依赖 + 生成 .env（已存在则跳过）+ 迁移 + 演示数据
make dev      # 启动开发服务器（热重载）
```

`make setup` 依次执行五个子目标：

| 步骤 | 命令 | 做了什么 |
|---|---|---|
| `venv` | `python3 -m venv backend/.venv` | 创建虚拟环境（已存在则跳过） |
| `install` | `pip install -r requirements.txt -r requirements-dev.txt` | 安装运行与开发依赖 |
| `env` | `cp .env.example .env` | **已存在则不覆盖** |
| `migrate` | `alembic upgrade head` | 建表到最新版本 |
| `seed` | `python scripts/seed_demo.py` | 写入演示数据（幂等，可重复执行） |

### 2.4 四个端的入口与账号

| 入口 | 地址 | 说明 |
|---|---|---|
| 统一登录页 | <http://localhost:8000/> | 未登录访问子端会被重定向到这里 |
| 平台端 | <http://localhost:8000/platform/> | 平台运营方 |
| 商户端 | <http://localhost:8000/merchant/> | 品牌方（租户） |
| 工厂端 | <http://localhost:8000/factory/> | 烧录工厂（跨租户） |

| API 交互式文档 | <http://localhost:8000/docs> | FastAPI 自动生成（OpenAPI） |
| 健康检查 | <http://localhost:8000/api/v1/health> | 容器健康检查用的就是这个 |

演示账号（**账号在 `.env` 中配置，密码是你自己设置的**）：

| 角色 | 账号变量 | 默认账号值 | 归属 |
|---|---|---|---|
| 平台超级管理员 | `PLATFORM_ADMIN_ACCOUNT` | `admin` | 全局长（`tenant_id` 为 `NULL`） |
| 平台运营 | `PLATFORM_OPERATOR_ACCOUNT` | `13812345678` | 平台 |
| 商户管理员 | `MERCHANT_ADMIN_ACCOUNT` | `13812345679` | t-001 星辰玩具 |
| 工厂管理员 | `FACTORY_ADMIN_ACCOUNT` | `13600000000` | 演示工厂 `f-demo-01` |

> ★ **全新种子下首次登录必然强制改密**（`FORCE_PASSWORD_CHANGE_ON_FIRST_LOGIN=true`）。
> 这是刻意设计：初始口令是一次性的。验收时如果不想改密，可以**直接改开发库**的
> `user_accounts.must_change_password = false`，而不是去改 `.env` 或改用弱口令。

### 2.5 验证装好了

```bash
make check     # 代码检查 + 类型检查 + 测试 + OpenAPI 契约一致性
make smoke     # 对**正在运行**的服务做 57 项冒烟断言
```

`make smoke` 要求服务已在运行（`make dev` 或 `make up`）。它按真实角色登录后逐端点请求，
以只读为主（例外是两个幂等写），并带**最低断言数守卫**——断言数不足 25 时判定脚本异常，
而不是打印「全部通过」。

## 3. Docker 部署

### 3.1 三种 profile

编排文件在**仓库根**（不是 `deploy/`），有三个 profile 可组合：

```bash
make up           # 应用（SQLite，零外部依赖）
make up-nginx     # 应用 + Nginx 前置（TLS / 缓存 / 多实例）
make up-full      # 应用 + Nginx + PostgreSQL
make down         # 停止（保留数据卷）
make down-clean   # ⚠️ 停止并删除数据卷
```

> **为什么编排文件在仓库根**：Compose 的三个相对路径——`build.context`、`env_file: .env`、
> `${VAR}` 插值读的 `.env`——**都以 compose 文件所在目录为基准**。放根目录时三者自然成立；
> 放进 `deploy/` 就要写 `..` 与 `../.env`，那是一类「换个目录执行就失效」的易错配置。
> **构建资产仍在 `deploy/`**（`Dockerfile.backend`、`nginx.conf`）——「编排入口在根、构建资产在 deploy/」是刻意分工。

### 3.2 默认方式（SQLite）

```bash
make env                       # 若还没有 .env
# 编辑 .env 设置三个强密码（同 ## 2.2）
make up
curl -s http://localhost:8000/api/v1/health
```

默认映射：应用 `8000`（可用 `APP_PORT` 改）；数据存在**命名卷** `toyverse-app-data` 的 `/data`。

### 3.3 加 Nginx

```bash
make up-nginx
# 经 Nginx：http://localhost:8080/platform/
# 直连应用：http://localhost:8000/platform/
```

Nginx 承担四件事（配置见 `deploy/nginx.conf`）：

| 职责 | 配置要点 |
|---|---|
| API 反向代理 | `/api/` 转到 `app:8000` |
| WebSocket 升级 | `location /ws/`（★ 真实路径是 `/ws/miniapp/chat`，**不在 `/api/v1` 前缀下**） |
| 静态资源缓存 | JS/CSS 用 `no-cache, must-revalidate`（**注意**：本项目前端文件名**不带内容哈希**，因此不能用 `immutable` 强缓存，否则发版后用户卡在旧代码且无法失效）；图片/字体 30 天 |
| SPA 回退 | `/platform/` `/merchant/` `/factory/` `/miniapp/` **各自**回退到自己目录的 `index.html` |

另外 `/login` 是**应用路由**而不是磁盘文件，配置里为它单独加了反代——否则经 Nginx 访问登录页会 404。

> ⚠️ **改完 `nginx.conf` 必须重启 Nginx 容器**：该文件是 bind-mount，`docker compose up -d` 不会因它变化而重建容器。
> ```bash
> docker compose restart nginx
> ```

### 3.4 加 PostgreSQL

```bash
make up-full
```

需要同时在 `.env` 里配好：

```ini
POSTGRES_PASSWORD=<强密码>
APP_DATABASE_URL=postgresql+asyncpg://toyverse:<强密码>@postgres:5432/toyverse_dev
```

> ⚠️ **`POSTGRES_PASSWORD` 在未启用 postgres profile 时也会参与 Compose 的变量插值**
> （插值是对整个文件进行的，与 profile 是否启用无关）。因此本项目**刻意没有**用
> `${POSTGRES_PASSWORD:?…}` 的强制语法——那会让「只想跑默认 SQLite 模式」的人直接起不来。
> 失败方向仍然是安全的：启用了 profile 却忘了配口令时，`postgres:16` 官方镜像自己会拒绝初始化并
> 打印「Database is uninitialized and superuser password is not specified」，**绝不会用空口令静默启动**。

### 3.5 ★ 容器专属变量（与开发用 `.env` 的区别）

这是本项目最容易搞错的一处。容器里有五个变量**不走**开发 `.env` 的语义：

| 变量 | 容器里的值 | 为什么不能用 `.env` 的值 |
|---|---|---|
| `APP_DATABASE_URL` | `sqlite+aiosqlite:////data/toyverse.db` | 开发机的 `DATABASE_URL` 是**相对路径**（`sqlite+aiosqlite:///./data/toyverse.db`），插值进容器会让 SQLite 落到镜像层 `/app/data/` 而非挂载卷 `/data/`，**容器重建即丢数据**。用独立变量名是刻意的 |
| `DATA_DIR` | `/data` | 容器里 `/app` 归 root、进程以非 root 运行，默认的 `<repo>/data` 建不出来 → `PermissionError` 崩溃循环 |
| `FRONTEND_DIR` | `/app/frontend` | 镜像布局是 `/app/app/...`（没有 `backend/` 这一层），靠「`__file__` 上溯几级」推算会数到 `/`，导致**整个 UI 404 而 API 正常** |
| `SEED_AT_STARTUP` | `false` | uvicorn 的 `--workers N` 会 fork N 个进程，**每个进程都跑 lifespan**；应用内播种会变成 N 进程同时往同一个 SQLite 灌种子（实测 1 成功 3 失败，且赢的那个可能只写一半） |
| `WORKERS` | `4` | worker 数按 CPU 核数与 SQLite 写并发权衡；SQLite 下不建议调大 |

注意 `sqlite+aiosqlite:////data/...` 里有**四个**斜杠——SQLAlchemy 的 URL 里前三个是 `://`，
第四个起才是绝对路径 `/data/...`。写成三个斜杠会变成相对路径，就退回上面第 1 条那个坑了。

### 3.6 镜像里发生了什么

`deploy/Dockerfile.backend` 是多阶段构建：

| 阶段 | 内容 |
|---|---|
| `builder` | `python:3.12-slim` + 建 `/opt/venv` + 装 `requirements.txt`（**先只复制依赖声明**，最大化利用层缓存） |
| `runtime` | 复制 `/opt/venv`、`backend/app`、`backend/alembic`、`alembic.ini`、`frontend`；建 `/data/storage` 并授权；以非 root 用户 `toyverse`（uid 10001）运行 |

启动命令（CMD）的顺序是刻意的：

```bash
alembic upgrade head && python -m app.db.seed && uvicorn app.main:app --workers ${WORKERS:-4}
```

**迁移 → 播种（一次）→ 多 worker 起服务**。播种放在 flask 之前执行一次，而不是交给应用 lifespan，
就是为了避开上面 `SEED_AT_STARTUP` 那条坑。

### 3.7 数据持久化

| 卷 | 容器内路径 | 内容 |
|---|---|---|
| `toyverse-app-data` | `/data` | SQLite 数据库 `toyverse.db` + 本地对象存储 `/data/storage` |
| `toyverse-postgres-data` | `/var/lib/postgresql/data` | PostgreSQL 数据目录 |

`make down` **不删卷**；`make down-clean`（`docker compose down -v`）才删。

## 5. 启动期安全校验：什么情况下服务拒绝启动

`app/core/config.py` 的 `validate_security()` 在应用启动时执行，失败即抛
`InsecureConfigurationError` 并**退出进程**。完整条件清单：

| # | 条件 | 触发时的报错方向 |
|---|---|---|
| 1 | `JWT_SECRET_KEY` 长度 < 32 字节，或含 `change-me` / `changeme` / `insecure` / `placeholder` / `example` / `secret-key` 等弱标记 | 明确指出是 JWT 密钥 |
| 2 | `QR_SIGN_SECRET` 长度 < 16 字节，或含同样弱标记 | 明确指出是二维码密钥 |
| 3 | `SECRET_ENCRYPTION_KEY` 非空但 < 32 字节或为占位符；**或为空且 `APP_ENV=production`** | 说明「更换 JWT 密钥会导致已加密的厂商密钥无法解密」 |
| 4 | 三个管理员口令未设置、长度 < `MIN_PASSWORD_LENGTH`、或命中常见弱口令表 | 逐项列出是哪个账号口令不合格 |
| 5 | **仅 `APP_ENV=production`**：`DEBUG=true` | 拒绝 |
| 6 | **仅 `APP_ENV=production`**：`SEED_DEMO_DATA=true` | 拒绝 |
| 7 | **仅 `APP_ENV=production`**：`CORS_ALLOWED_ORIGINS` 含 `localhost` 或 `127.0.0.1` | 拒绝 |
| 8 | **仅 `APP_ENV=production`**：`MINIAPP_SMS_PROVIDER=mock` 或 `PAYMENT_PROVIDER=mock` | 拒绝（避免生产环境用假短信/假支付） |
| 9 | 运行时目录不可写：`DATA_ROOT`、存储根、SQLite 父目录任一 `PermissionError` | 由 `ensure_runtime_dirs()` 抛出**可操作**的配置错误（而不是崩溃循环） |

> **设计意图**：这一类问题的共同点是「配置错了但服务照常跑」，后果往往在几天后才以数据事故的形式暴露
> （假短信发出了、密钥写进了日志、演示数据混进了生产库）。因此本项目的选择是**在启动瞬间失败**。

## 7. 故障排查

以下每一条都是本项目在**真跑一遍**时实际踩到的，不是泛泛的检查清单。

### 7.1 容器重建后数据没了

| 现象 | 最可能的原因 | 排查动作 |
|---|---|---|
| `make down && make up` 后租户/设备数变回初始值，或直接报数据库不存在 | `.env` 的 `DATABASE_URL` 是**相对路径**，被 `${DATABASE_URL}` 插值带进了容器 → SQLite 落在镜像层 `/app/data/` 而不是挂载卷 `/data/` | 检查 compose 里是否用的是 `APP_DATABASE_URL`（默认 `sqlite+aiosqlite:////data/toyverse.db`，注意**四个斜杠**）；`docker compose exec app env \| grep DATABASE_URL` 确认容器内的实际值 |

### 7.2 经 Nginx 访问登录页 404，但直连 8000 正常

| 现象 | 原因 | 排查动作 |
|---|---|---|
| `http://localhost:8080/login` → 404 | `/login` 是**应用路由**而不是磁盘文件，Nginx 的静态托管找不到它 | 确认 `deploy/nginx.conf` 里有 `location = /login` 的反代；改完配置要 `docker compose restart nginx`（bind-mount 不会自动重载） |

### 7.3 界面全部 404，但 API 完全正常

| 现象 | 原因 | 排查动作 |
|---|---|---|
| `/api/v1/health` 返回 200，但 `/platform/` 返回 404；日志里只有一条 WARNING | 前端的 `FRONTEND_ROOT` 靠「`__file__` 上溯固定级数」推算，而容器布局是 `/app/app/...`（**没有 `backend/` 这一层**），于是数到了 `/` | 确认容器里设了 `FRONTEND_DIR=/app/frontend`；本机跑时可用同一变量覆盖 |

### 7.4 WebSocket 握手拿回一段 HTML

| 现象 | 原因 | 排查动作 |
|---|---|---|
| 小程序对话页连不上；用工具看握手响应体是 HTML | Nginx 的 WS location 与实际路径不符——真实路径是 `/ws/miniapp/chat`，**不在 `/api/v1` 前缀下** | `deploy/nginx.conf` 应为 `location /ws/`；验证方式见 `## 7.7` |

### 7.5 冒烟脚本报「登录失败」，但同一口令用 curl 能通

| 现象 | 原因 | 排查动作 |
|---|---|---|
| `make smoke` 说登录失败，手工 curl 同一账号口令成功 | 脚本里的 JSON 取值函数曾经把程序与响应体**同时喂给 stdin**，导致取值恒为空 | 本项目已修（改用 `python3 -c` 传程序、stdin 留给数据）。若你改过脚本，先用 `bash -x` 确认取值函数拿到的是非空字符串 |

> ★ 这个坑的教训值得记：**会静默通过的检查比没有检查更危险**。因此 `smoke_test.sh` 现在带
> `MIN_EXPECTED_CHECKS=25` 守卫——断言数不足时判定「脚本异常」，而不是打印「全部通过」。

### 7.6 容器起不来 / 一直重启

按顺序查：

```bash
docker compose ps                 # 看状态与健康检查
docker compose logs --tail=100 app
```

| 日志里的关键词 | 含义 | 处理 |
|---|---|---|
| `InsecureConfigurationError` | 启动期安全校验拒绝 | 对照 `## 5.` 的清单逐项修 |
| `PermissionError` + `/data` 或 `/app/data` | 目录不可写（非 root 运行） | 确认 `DATA_DIR=/data` 且卷已挂上 |
| `Database is uninitialized and superuser password is not specified` | 启用了 postgres profile 但没配 `POSTGRES_PASSWORD` | 补 `.env` 的 `POSTGRES_PASSWORD` |
| `写入演示数据失败` × N | 多 worker 各自播种（并发写同一 SQLite） | 确认 `SEED_AT_STARTUP=false`，播种在 CMD 里 fork 前执行一次 |

### 7.7 怎么确认 WebSocket 真的通了

用 Python 客户端（**注意令牌走 query 参数**，因为浏览器 WebSocket 不能带自定义 header）：

```bash
python3 - <<'PY'
import asyncio, websockets

async def main():
    # 用真实的小程序令牌替换 <TOKEN>；非法令牌应当被以 4401 关闭
    url = "ws://localhost:8080/ws/miniapp/chat?token=<TOKEN>&deviceId=<DEVICE_ID>"
    try:
        async with websockets.connect(url) as ws:
            print("握手成功：", await ws.recv())
    except Exception as e:
        print("被拒绝/异常：", e)

asyncio.run(main())
PY
```

✅ **预期**：握手建立成功；若令牌非法，服务端以关闭码 `4401` 结束连接——**而不是返回一段 HTML**。
后者说明请求落到了 SPA 回退，即 `## 7.4` 那个配置问题。

## 8. 升级与回滚

### 8.1 升级

```bash
git pull
make install                  # 依赖可能变了
make migrate                  # 应用新迁移
make check                    # 门禁：lint + 类型 + 测试 + 契约
make up                       # 或 docker compose up -d --build
make smoke                    # 确认服务与端点都正常
```

### 8.2 回滚

```bash
# 1) 停止服务（保留数据卷）
make down

# 2) 回滚代码
git checkout <上一个可用提交>

# 3) 回滚数据库（逐版本回退；先确认目标版本号）
cd backend && python -m alembic downgrade -1      # 回退一版
python -m alembic current                          # 确认当前版本

# 4) 重新起服务并冒烟
make up && make smoke
```

> ⚠️ **回滚前先备份数据库**。SQLite 直接复制 `data/toyverse.db`（容器用 `docker compose cp`）；
> PostgreSQL 用 `pg_dump`。`alembic downgrade` 会执行迁移文件里写的 `downgrade()`，
> 而**丢列/丢表类的迁移回滚是有损的**（数据不会回来）。
> 本项目所有迁移都实现了 `downgrade()` 并通过「升降往返可逆」验证，但那只保证**结构**可逆。

### 8.3 备份建议

| 场景 | 命令 |
|---|---|
| SQLite（开发/单机） | `cp data/toyverse.db data/backups/$(date +%Y%m%d%H%M%S)/toyverse.db` |
| SQLite（容器） | `docker compose cp app:/data/toyverse.db ./backup-toyverse.db` |
| PostgreSQL | `docker compose exec -T postgres pg_dump -U toyverse toyverse_dev > backup.sql` |
| 对象文件（知识库 / 固件包） | 复制 `STORAGE_LOCAL_ROOT` 整个目录 |

> ⚠️ `scripts/reset_db.sh` 的备份是**同盘备份**：宿主机磁盘故障时备份与数据一起丢。
> 生产应改为异机或对象存储备份（见 `## 9.`）。

## 附录：已知局限与取证边界

1. ✅ **PostgreSQL 已完成真跑验证**（原为「只验证了配置可解析」）：`docker compose --profile postgres`
   起真实 PG 16，迁移跑到 `0015`、种子写入、应用 healthy、**冒烟 57/57 全通过**；
   并因此发现并修复了一个 PG 专有缺陷（日期被当字符串绑定，SQLite 上不可复现）——
   详见 `11-测试与质量保障.md` 的 `## 7.5`。
   ✅ **并发写也压测过了**：写 **93.0 QPS / 0 失败**，对照 SQLite 的 **30.7 QPS / 4×500**
   （`## 3.4` 与 `11-测试与质量保障.md` 的 `## 8.1`）。
   ⚠️ 仍未做的是：**连接池参数调优**、**「多实例 + PG」组合**、**长时间稳定性**。
2. ✅ **Nginx TLS 与多实例均已实测**（P11 收尾）：
   TLS 四项全过（HTTPS API/SPA 200、HTTP→HTTPS **301**、`wss://` 握手 → **4401**、`TLSv1.3`）；
   多实例轮询 **31 / 29**、WS 经 Nginx 正常。
   ★ **但多实例实测给出反面结论**：两实例**共享同一 SQLite 卷**时写吞吐**无提升**（31.4 QPS）
   且出现 **2×500**（`database is locked`）→ **多实例必须配 PostgreSQL**。
   ⚠️ 证书是**自签**的（`CN=localhost`），仓库**未附证书**，`## 9.2` 的演练步骤仍需自行签证书。
3. ✅ **CI 已在真实 GitHub 上跑通**（2026-09-17，run #1 五 job 全绿）。
   ★ 首次真跑即发现：`ci.yml` 的触发分支写的是 `master`、而默认分支是 `main`，
   因此**推送不触发 CI**；已改为 `main`。详见 `11-测试与质量保障.md` 的 `## 5.2`。
   ⚠️ CI 不构建镜像，且 `ubuntu-latest` 与本机不是同一环境。
4. **冒烟脚本只覆盖读路径**（外加两个幂等写）。
   → 后果：`make smoke` 通过**不代表**写路径正确；写路径依赖 `make test`（隔离测试库）。
5. ★ **容器内 4 个 uvicorn worker + SQLite 的写并发已被量化**（P11 收尾实测）：
   20 并发写同一行 → **30.7 QPS、4/487 返回 `500`**（`database is locked`）；切 PostgreSQL 后
   **93.0 QPS、0 失败**。**加 worker 无用**，加实例更糟（无提升且冲突翻倍）。
   → 后果：演示与轻负载无问题；**真实多租户并发写必须切 PostgreSQL**（`## 3.4`）。
   → 补齐方式：设 `DATABASE_URL` 指向 PostgreSQL，并按 `## 9.2` 视需要横向扩展。
6. **`make reset-db` / `scripts/reset_db.sh` 的备份是同盘备份**。
   → 后果：宿主机磁盘故障时数据与备份一起丢。
   → 补齐方式：改用异机或对象存储备份。
7. **`STORAGE_BACKEND=s3` 当前是显式安全失败**（`S3Storage` 不假装可用）。
   → 后果：知识库文件与 OTA 固件包只能用本地磁盘存储。
   → 补齐方式：补齐 S3 实现，或继续用 `local` + 挂载持久卷。
8. **演示数据的固件包没有上传文件**，因此 OTA 推送会**如实失败**（每台报「固件包没有上传文件，无法推送」）。
   → 这是 ADR-07 的预期表现，不是缺陷；要演示成功路径需先上传一个真实固件文件。
9. **文档与代码的一致性由 `make docs-check` 保证**，但本指南里的**叙述性描述**无法自动校验。
   → 改动部署方式时，请同步更新本文档（并把 `docs/` 加入该 PR 的必改清单）。
