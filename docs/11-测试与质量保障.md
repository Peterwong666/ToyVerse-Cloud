## 0. 结论先行

### 0.1 八道门禁

| 门禁 | 命令 | 实测结果 |
|---|---|---|
| 代码规范 | `make lint` | ✅ ruff 0 问题（含 `tests/` 与 `scripts/`） |
| 静态类型 | `make typecheck` | ✅ mypy **strict**，**95 个源文件**无问题 |
| 测试 | `make check` | ✅ **814 passed**（`make check` 单次实测 `814 passed in 256.49s`） |
| 接口契约 | `make openapi-check` | ✅ 实现与快照一致（**119 paths / 145 operations**） |
| 前端导入契约 | `make fe-check` | ✅ **399 处** import 全部匹配 |
| 文档一致性 | `make docs-check` | ✅ 端点 / 表 / 错误码 / 权限码 / 枚举值 / 引用 / 边界声明 |
| 迁移一致性 | `python -m alembic check` | ✅ 模型与迁移**零漂移**；升降往返可逆 |
| 敏感信息 | `scripts/scan_secrets.py` | ✅ **247 个被跟踪文件 0 命中** |

> `make check` = `lint` + `typecheck` + `test` + `openapi-check` + **`docs-check`**（五个子目标）。
> 其中 `docs-check` 是本阶段新增的文档一致性门禁 —— **文档与代码脱节会让主门禁红灯**。

### 0.2 ★ 最需要如实说明的一个数字

| 项 | 值 |
|---|---|
| **总覆盖率** | **70%**（10501 语句 / **3141 未覆盖**） |
| 覆盖率最低的三个服务 | `ai_config_service` **29%**、`metrics_service` **29%**、`ota_service` **30%** |

> ★ **814 个用例全绿 ≠ 测试充分。**
> 本项目的覆盖率只有 70%，且三个 P9 服务低于 31%。
> 原因是这些域的分支多（Wi-Fi/4G 差异、分区保存、快照重建、逐台推送），
> 而测试集中在**主路径与关键守卫**（隔离、幂等、安全失败），**长尾分支未覆盖**。
> 任何引用本文的人都不应把「814 passed」读成「质量已充分保障」。

### 0.3 两个测试计数口径（必须区分）

| 口径 | 数值 | 含义 |
|---|---|---|
| **测试函数** | **553** 个（26 个文件） | 源码里 `def test_...` 的个数 |
| **测试用例** | **814** 个 | pytest 实际执行的用例数，**差额来自 `@pytest.mark.parametrize` 展开** |

例：租户隔离矩阵用 `parametrize` 把「端点 × 越权形态」展开，
一个测试函数可能对应几十个用例。**两个数字都对，只是口径不同。**

### 1.4 端到端（1 个文件 / 1 个函数）

`test_full_loop.py` —— 一条测试串完主干：

> 客户开通与授权 → 云服务商 → 产品模板 → 授权 → 客户产品 → 商户下单 → 平台审核 →
> 生成设备（Wi-Fi 本地 SN）→ 入库 → 派单工厂 → 烧录上报 → 抽检 → 出货 →
> 分配（`SHIPPED → ALLOCATED`）→ 终端用户登录 → 扫码解析 → 激活并绑定 →
> SSE 流式对话 → 会话与消息落库 → 设备四维终态与七种时间线事件

**两个设计要点**：

| 要点 | 说明 |
|---|---|
| **逐步断言而非只断结果** | 任一环断裂都能从断言消息定位到具体环节 |
| **含脱敏红线** | 全程断言工厂端响应不出现客户名 / 联系方式 / 金额字段 |

> ⚠️ **只有 1 条用例**：它证明「主干能通」，**不证明分支正确**。
> 分支靠 integration 层覆盖。

### 2.3 为什么会这样（根因，不是借口）

| 原因 | 具体表现 |
|---|---|
| **分支密度高** | `ai_config_service` 要处理「供应商 / 提示词 / 角色 / 音色 / 内容安全」五个分区 × 两种联网方式（Wi-Fi 不支持角色） |

> ① 先给 `metrics_service` 的聚合分支补参数化用例（`P-07` 的守卫已在那，扩展成本低）；
> ② `ota_service` 补 `PARTIAL_FAILED` 与推送中断；
> ③ `ai_config_service` 补五个分区的独立保存与联网方式差异。

## 3. 租户与工厂隔离矩阵

### 3.1 两条防线

```mermaid
flowchart TB
    subgraph m1["① 参数化隔离矩阵"]
        P["对每类越权形态<br/>用租户 A 的令牌访问租户 B 的资源"]
        P --> A1["断言 404<br/>（不是 200，也不是 403）"]
    end
    subgraph m2["② 路由元测试"]
        R1["读 app.routes 拿全部已注册路径"]
        R2["读测试里的覆盖清单"]
        R3["★ 双向比对：差集非空 → 红灯"]
    end
```

### 3.2 覆盖的越权形态

| 形态 | 例子 | 覆盖阶段 |
|---|---|---|
| **路径参数** | `GET /merchant/devices/{他人的 device_id}` → 404 | P5 |
| **查询参数** | `GET /merchant/metrics/overview?productId=<他人的产品>` → 404 | ★ **P9 首次覆盖** |
| **跨厂** | 工厂 A 访问工厂 B 的工单详情 / 二维码 / 烧录 → 404 | P6 |
| **列表范围** | 他人租户设备列表返回 0 条（而不是 403） | P5 |
| **令牌类型** | 小程序令牌调管理端接口 → 401；管理端令牌调小程序接口 → 401 | P8 |

★ **「查询参数形态的越权」值得单独强调**：路径参数越权比较直观，
但 `?productId=<他人的产品>` 这种形态**不改变路径、只改变筛选条件**。
如果服务层没校验参数归属，泄漏的**不是一条资源，而是他人的全部数据**。
这是本项目在 P9 才第一次覆盖的盲区。

### 3.3 路由元测试（防「静默漏测」）

```python
# 思路（伪代码）
registered = {r.path for r in app.routes}
declared   = load_covered_paths_from_test_matrix()
assert registered - declared == set()   # 有端点没被覆盖 → 红灯
assert declared - registered == set()   # 清单里有不存在的端点 → 红灯
```

> **为什么这条元测试至关重要**：矩阵测试的价值完全取决于「清单是否完整」。
> 新增了端点却忘了加进清单，**矩阵依然全绿**——它只是没测而已。
> 双向比对把这种「静默漏测」变成红灯。
>
> 这与本项目的一条通用教训一致：**会静默通过的检查比没有检查更危险。**

## 4. 契约测试与门禁

### 4.1 四类契约

| 契约 | 实现 | 门禁 |
|---|---|---|
| **接口契约** | `tests/contract/openapi_snapshot.json`（★ 在**仓库根**，不在 `backend/`） | `make openapi-check` |
| **前端导入契约** | 每个 `import` 的路径存在、具名导出确实被导出 | `make fe-check` |
| **数据库契约** | ORM 模型 ↔ Alembic 迁移 | `alembic check`（零漂移） |
| **文档契约** | 文档声明的端点 / 表 / 错误码 / 权限码 / 枚举值 / 引用 | `make docs-check` |

### 4.2 接口契约为什么必须门禁

```mermaid
flowchart LR
    CHANGE["改动路由 / schema / docstring"] --> EXP["make openapi"]
    EXP --> SNAP["openapi_snapshot.json"]
    SNAP --> CHK{"make openapi-check"}
    CHK -->|一致| PASS["✔"]
    CHK -->|有差异| FAIL["✘ 必须有人显式确认这次变更"]
```

**前端是按契约写的**，因此「接口悄悄变了」就是破坏性变更。

> ⚠️ **一个容易忽略的点**：**改端点的 `docstring` 或字段描述也会让快照过期**。
> 这类差异不会被任何类型检查发现——只有 `make openapi-check` 会报出来。

### 4.3 `make docs-check` 的八类校验

| # | 校验 | 不一致的后果 |
|---|---|---|
| 1 | `docs/06` 的端点表格与方法/路径 vs **OpenAPI 快照**（双向） | 读者照文档调接口会 404 |
| 2 | `docs/05` 字段字典的表名集合 vs 迁移/模型（**并在脚本内交叉校验迁移与模型一致**） | 读者照文档写 SQL 会报表不存在 |
| 3 | `docs/06` 的错误码 vs `ErrorCode`，**且校验文档写的 HTTP 状态与 `_STATUS_MAP` 一致** | 前端按错误码做的分支永不命中 |
| 4 | `docs/07` 的权限码 vs `permissions.py`（双向），**并检查有没有写错格式的权限码** | 配权限时发现码不存在 |
| 5 | `docs/05` 状态枚举小节的取值 vs `enums.py` 成员 | 文档描述的状态根本不存在 |
| 6 | 文档引用的 `make <target>` / `scripts/<file>` / 相对链接是否存在 | 链接 404、命令报 no rule |
| 7 | `docs/11` 的**逐文件测试用例数** vs 源码，且三个分组的文件数/函数数都对得上 | 读者核对数字时发现对不上 |
| 8 | 每份 `docs/NN-*.md` 是否含「已知局限 / 取证边界」；是否引用了不上传目录的内部路径 | 边界声明被漏写；不该上传的目录被引用 |

> ★ **这门禁自己也被验过，而且改过两次**：
> ① 首跑报出 5 处问题（含一处会让分组合计对不上的手写数字错误），因此**第 7 类校验是被一次真实错误逼出来的**；
> ② 第 4 类的「格式写错」子检查同样来自一次真实错误——文档里把 `factory:batch:read`
> 写成了**少一段冒号**的形式（`factory` + `:` + `batch` 后直接接了动作，缺了资源与动作之间的分隔），
> 而当时的正则**只匹配格式正确的权限码**，于是这个错码**静默通过**了。
> **教训：只校验「正确的形状」会漏掉「形状都不对」的输入。**

## 5. CI 流程

### 5.1 五个并行 job

```mermaid
flowchart LR
    PUSH["push / PR"] --> L["lint<br/>ruff + mypy strict"]
    PUSH --> T["test<br/>pytest 全量 + e2e"]
    PUSH --> C["contract<br/>openapi 快照"]
    PUSH --> F["frontend<br/>ES Module 导入校验"]
    PUSH --> S["secrets<br/>敏感信息扫描"]
```

| job | 命令 | 为什么独立 |
|---|---|---|
| `lint` | `ruff check` + `mypy app` | 20–40 秒，**反馈最快**；挂了不必等测试跑完 |
| `test` | `pytest -q` + `pytest tests/e2e` | 分钟级 |

## 7. 本项目的测试方法论

### 7.1 ★ 代理自测全绿 ≠ 功能可用

本项目在 P4–P9 期间采用「主会话 + AI Agent 并行」的开发方式（AI Agent 写代码与测试）。
**实测结论**：

| 阶段 | AI Agent 交付 | 结果 | 真缺陷由谁发现 |
|---|---|---|---|
| P6 | 275 条测试**全绿** | 代理报告完成 | **3 个真缺陷全部由主会话的端到端验收 / 浏览器实测发现** |
| P8 | 20 条测试**全绿** | 代理报告完成 | **1 个真缺陷由浏览器实测发现**（「激活成功但对话被拒」） |
| P9 | 46 条测试**全绿** | 代理报告完成 | **3 个真缺陷由主会话发现**（含 1 个由自己的测试断言发现） |
| P10 | —— | —— | **12 个问题全部只能靠真跑 Docker 发现** |

**为什么会这样**：

| 原因 | 说明 |
|---|---|
| 自动化测试覆盖的是「**我以为的路径**」 | 测试写的是实现者脑子里的流程；真实使用会走别的路径 |
| 静态检查查不出**配置与环境的错** | `make up` 坏了 10 个阶段，任何一个 lint / typecheck / test 都不会报 |
| 界面问题只有渲染出来才看得见 | 按钮文案、动作是否随状态更新、脱敏后的观感 |

### 7.2 ★ 会静默通过的检查比没有检查更危险

| 事件 | 后果 | 对策 |
|---|---|---|
| 冒烟脚本在**误删计数函数**后仍打印「0 通过 / **全部通过**」 | 一个**已经失效的检查**持续给出绿色信号 | 加 `MIN_EXPECTED_CHECKS=25` 守卫：断言数不足即判「脚本异常」 |
| 一条 flaky 测试（约 1/16 概率假通过，因为篡改末位时末位本来就是 `0`） | 一个**会随机不变换**的用例比没有用例更糟 | 改为显式翻转末位，**并断言「改动确实发生」** |
| 敏感信息扫描器首版报 133 条误报 | 规则太宽 → 真泄露会被淹没 | 收敛规则，**并补一个「规则确能命中」的自测** |

**共同规律**：三件事都是「检查本身可能有毛病」。
因此本项目的一条做法是——**让检查能区分「规则不响」与「规则坏了」**。

### 7.3 其它四条做法

| # | 做法 | 具体体现 |
|---|---|---|
| 1 | **把不变量钉成单测，两侧必须同改** | 「可冻结集合 == `ASSET_TRANSITIONS[FROZEN]`」（`test_device_state_machine.py`）；「序列化白名单 == 响应模型 `model_fields`」（`test_mask.py`） |
| 2 | **给「数据不存在」加对照实验** | `test_factory_desensitize.py` 会同时断言**平台端能看到客户名**——否则「工厂端看不到」可能只是因为**数据本来就没写** |
| 3 | **用同一断言守住「两条路径必须一致」** | `test_metrics_isolation.py` 的核心断言「**快照之和 == 实时聚合**」——用系数摊派的实现**过不了**这条 |
| 4 | **拒绝写入断言也要有** | `test_ota.py` 断言 Wi-Fi 推送 409 且**不留任何推送记录**——「拒绝」必须是真的没发生 |

### 7.5 ★ 有些缺陷在 SQLite 上永远复现不出来

本项目默认用 SQLite、可选 PostgreSQL（`ADR-05`）。**这个组合有一个结构性盲区**：
SQLite 是**动态类型**，而 PostgreSQL 严格 —— 同一段 SQL 在 SQLite 上能跑、在 PG 上报错。

**真实案例（P11 公开前真跑 PG 时由冒烟发现）**：

| | |
|---|---|
| 代码 | `metrics_service.py` 的 `_date_between`：`func.date(col).between(date_from.isoformat(), date_to.isoformat())` |
| 在 SQLite 上 | `func.date()` 返回 **TEXT**（`'2026-09-17'`），字符串比字符串 → **完全正常**，804 个用例全绿（当时的用例总数） |
| 在 PostgreSQL 上 | `func.date()` 返回真正的 **date**，与 `varchar` 比较 → `UndefinedFunctionError: operator does not exist: date >= character varying` |
| 后果 | 运营看板的**概览与快照重建两个端点直接 500**，而这些是最核心的页面 |
| 修复 | 绑定 `date` 对象而不是 `.isoformat()` 字符串——两种方言都正确（SQLite 方言渲染成 ISO 字符串，PG 方言绑定为 `date`） |

**怎么守住它**：`tests/unit/test_sql_dialect_portability.py` **不测行为、测绑定参数的类型**——
把 `_date_between` 用 PG 方言编译，断言所有绑定参数都是 `date` 而非 `str`。
这条断言在旧实现上会失败（已实测：旧写法绑定 `str` → 被拦下；新写法绑定 `date` → 通过）。

> 📌 **为什么不能靠「跑一遍测试」**：这类缺陷的触发条件是**数据库方言**，而 CI 与本地都跑 SQLite。
> 能抓住它的只有两件事：① **真跑一次 PG**（本项目的做法，已纳入公开前的必做验证）；
> ② **把「不该是字符串」这种类型约束写成不需要数据库的单测**。
>
> ★ 这也修正了本项目早先的一个判断：P10 曾把「PostgreSQL 只验证了配置可解析」列为可接受的局限，
> 认为「SQLite 全链路已实测」就够了。**实际上不够——一个核心页面在 PG 上直接 500。**
> 「配置能解析」与「服务能跑」之间的差距，比想象的更大。

### 8.1 负载测试：SQLite vs PostgreSQL

**方法**（两侧口径完全一致）：

| 项 | 值 |
|---|---|
| 并发 | **20** |
| 每轮时长 | **15 秒** |
| 读路径 | `GET /api/v1/platform/devices` + `GET /api/v1/platform/orders` |
| 写路径 | `POST /api/v1/platform/devices/d-demo-01/simulate-heartbeat`（对**同一台设备**写，故意制造争用） |
| 服务 | 本机 uvicorn，**4 worker**，前后端同进程 |
| 数据库 | SQLite：`/tmp` 下的临时库；PostgreSQL：`docker compose --profile postgres` 起真实 PG 16 |
| 局限 | 单机、默认配置、无外部流量干扰 —— **不能当容量规划依据**（见 `## 8.5`） |

**结果**：

| 指标 | SQLite | PostgreSQL | 说明 |
|---|---|---|---|
| 读 QPS | **73.6** | **72.0** | **基本持平**（差 2%，落在噪声内） |
| 读 p50（ms） | 257 | **149** | PG 中位更低 |
| 读 p95 / max（ms） | **436 / 904** | 994 / 2339 | ★ SQLite **尾延迟明显更好** |
| 读失败 | 0 / 1125 | 0 / 1095 | 都全通过 |
| 写 QPS | **30.7** | **93.0** | ★ PG **约 3 倍** |
| 写 p50 / p95（ms） | 210 / **2946** | 151 / **606** | ★ SQLite 写队列堆积 |
| 写失败 | **4 / 487**（`500`） | **0 / 1414** | ★ SQLite 报 `database is locked` |

> ★★ **一个与直觉相反、值得记录的结果：读路径上 SQLite 毫不逊色。**
> 本项目一度默认假设「PG 全面更快」，这次实测打破了它——读吞吐持平；
> PG 的**中位**延迟更低（149 vs 257 ms），但 SQLite 的**尾**延迟好得多
> （p95 436 vs 994 ms、max 904 vs 2339 ms），也就是 SQLite 更「稳」、PG 的读长尾更长。
> **PG 的优势完全集中在写路径**：写吞吐 ×3、失败归零、p95 从 2.9 s 降到 0.6 s。
> 所以选型结论应当精确写成「**只有需要并发写时才必须上 PostgreSQL**」，
> 而不是含混的「PG 什么都更快」——后者会让「读多写少的小部署用 SQLite」这条合理选择看起来像妥协。

**SQLite 的 4 个写失败是什么**：服务端日志是
`sqlite3.OperationalError: database is locked`，最终以 `500` 返回。
原因是 SQLite 的写锁是**整库级排它锁**，20 并发写同一行时抢锁超时。
加 worker 也救不了——**worker 越多，抢锁越凶**（`## 8.3` 直接验证了这一点）。

### 8.2 Nginx TLS

用**自签证书**（`CN=localhost`）验证「TLS 终止 → 反代 → WS upgrade」这条链路。四项全过：

| # | 验收项 | 结果 |
|---|---|---|
| ① | HTTPS 提供 API（`/api/v1/health`） | **200** |
| ② | HTTPS 提供 SPA 与静态资源（4 个端 + `/login` + `shared/core/api.js`） | 全部 **200** |
| ③ | HTTP → HTTPS 重定向 | **301**，`Location: https://…` |
| ④ | ★ **`wss://` WebSocket 握手** | 握手成功，服务端以 close code **4401** 关闭（期望 4401 = 非法令牌） |

`openssl s_client` 佐证确实走了 TLS、没有静默回退到明文：
`New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384`。

> ④ 是这一组里最有价值的一条：它证明 **TLS 终止与 `Upgrade: websocket` 同时正确**。
> 「配了 TLS 之后 WebSocket 静默失效」是反代最常见的坑之一（`proxy_set_header Upgrade`
> 与 `Connection` 漏配时，普通请求全 200、只有实时链路不通）。

### 8.3 多实例负载均衡

2 个应用实例 + 1 个 Nginx（轮询 `upstream`）：

| # | 验收项 | 结果 |
|---|---|---|
| ① | 请求是否真的分发到两个实例 | **31 / 29**（各打 60 次，两边都 > 0） |
| ② | WebSocket 经 Nginx | 握手成功 → **4401** |
| ③ | ★ 两实例**共享同一 SQLite 卷**时的并发写 | **31.4 QPS + 2×500**；两实例日志各 3 条写冲突 |

> ★ **第 ③ 项是反面结论，也是本次最重要的部署结论**：
> **加实例救不了 SQLite 的写并发**——单实例 30.7 QPS，双实例 31.4 QPS（**没有提升**），
> 而写冲突**翻倍**（两实例合计 6 条）、p95 从 2946 ms 涨到 2736 ms 后仍有 500。
> 结论：**多实例部署必须配 PostgreSQL；SQLite 只适合单实例。**
> 这条比「Nginx 能轮询」有价值得多——轮询能通是配置问题，写并发不行是**存储层的硬约束**。

#### 8.3.2 多实例 + PostgreSQL（2026-09-18 补测）

| # | 验收项 | 结果 |

### 8.4 ★ 一次真跑才会暴露的缺陷：初始账号播种不幂等

这一项**不是压测发现的，是上面 8.3 的多实例实验顺带炸出来的**，但价值高于任何 QPS 数字。

| | |
|---|---|
| 现象 | 复用已有数据卷启动容器 → 应用**启动即崩、无限重启**（`Restarting (1)`） |
| 根因 | `_seed_admin_users` **按 `account` 查重、却按固定 `id` 插入**——两个判据不一致 |
| 触发条件 | `.env` 里把商户管理员的**登录账号换成了另一个号码**；按新名字查 → 查不到 → 认为「还没有」→ 拿同一个固定 `id` 再插一次 → `IntegrityError: UNIQUE constraint failed: user_accounts.id` |
| 为什么严重 | 容器入口脚本是「**先播种、再起服务**」，所以**改一次 `.env` 里的账号名，已有库的部署就再也起不来**——一个配置项就能让线上服务进入无限重启 |
| 修复 | 查重一律按 **`id`**；三条路径都覆盖：同名 → 空操作（**不动密码**）、改名 → 同步登录名并告警、目标名字已被**别的 `id`** 占用 → 跳过并告警 |
| 实测验证 | ① 在**真实的故障卷**上复现并修复：应用从 `Restarting (1)` 变为 `healthy`，日志出现改名告警，`password_hash` 前后一致，再次重启为幂等空操作；② 新增 `tests/integration/test_seed_admin_users.py`（**5 条**）把四条路径钉死 |

**回归守卫是「证明过」的**：`test_renamed_account_is_synced_instead_of_crashing`
在**修复前**的实现上会失败（实测输出正是 `UNIQUE constraint failed: user_accounts.id`），修复后通过。
这就是 `## 7.5` 那条经验的又一个实例——
**这类缺陷在单元测试、在 SQLite 冒烟、在 4 个 worker 的本地服务里都看不见，只有真跑容器、且复用已有数据卷时才炸。**

### 8.5 这一节**仍然没有**证明的事

| 项 | 说明 |
|---|---|
| ⚠️ **不是容量规划依据** | 单机、默认配置、无调优、每轮仅 15 秒；**不要**用这些 QPS 推算线上容量 |
| ⚠️ **未调连接池与 worker 数** | PG 连接池参数、`--workers` 取值都**没有**做扫描实验 |

| ✅ **已测「多实例 + PostgreSQL」** | 2026-09-18 验证：2 实例 + Nginx + PG，读 142.5 QPS / 0 失败，写 66.2 QPS / 1000/1000 成功，请求分发 503/502，WS 经 Nginx 4401 |
