## 1. 协议规格（已取证）

**取证来源**：火山引擎文档中心《通过标准协议自定义接入》
（实时音视频 → 硬件对话智能体 → 开始使用 → 快速集成），
经浏览器实际打开读取，页面标注「最近更新时间：2026.07.29」。
**取证时间**：2026-09-20。

### 1.1 前置凭证

接入需要四样东西（均在火山控制台获取）：

- **InstanceID** — 物联网实例的全局唯一标识
- **product_key** — 产品标识符
- **product_secret** — 产品密钥，**用于设备注册阶段的签名**
- **bot_id** — 指定要连的具体智能体

> ⚠️ 官方原文明确：`product_secret` **切勿泄露或直接硬编码在客户端代码中**。

### 1.2 步骤 1：注册设备（DynamicRegister）

用产品级密钥换取**设备级独享密钥 `device_secret`**，该密钥是后续 WebSocket 鉴权的唯一凭证。

| 项 | 值 |
|---|---|
| 方法 | `POST` |
| 地址 | `https://iot-cn-shanghai.iot.volces.com/2021-12-14/DynamicRegister` |
| Query | `Action=DynamicRegister`、`Version=2021-12-14` |

Body 字段：`InstanceID`、`product_key`、`device_name`（自定义，单产品内唯一）、
`random_num`、`timestamp`（**毫秒**）、`auth_type`（固定 1）、`signature`。

签名算法（官方给出 Python 参考）：

```
content = "auth_type={auth_type}&device_name={device_name}&random_num={random_num}"
          "&product_key={product_key}&timestamp={timestamp}"
signature = base64( HMAC-SHA256(key=product_secret, content) )
```

**响应**：`Result.payload` 是**加密后的 device_secret**（Base64 字符串）——需自行解密：

- 算法：**AES-CBC**，PKCS7 填充
- 密钥：`product_secret` 的**前 16 字节**
- IV：同上的**前 16 字节**（即 IV == key）
- 另有 `Result.rtc_app_id`

**错误码**：`15000010`（产品未开始动态注册）、`15000020`（签名验证失败）、
`12000140`（License 已过期）、`12000020`（设备名不合规）、`12000130`（License 已耗尽）。
设备名规范：`^[a-zA-Z0-9_\-.:@]{1,128}$`。

> 官方提示：`device_secret` 需在设备端**持久化加密存储**，避免每次重启都重新注册。

### 1.3 步骤 2：建立 WebSocket 连接

| 项 | 值 |
|---|---|
| 地址 | `wss://ai-gateway.vei.volces.com/v1/realtime` |
| Query | `bot=<bot_id>`（**必填**）、`wait_for_session_update`（可选，true 则等待 `session.updated`，超时 10 秒） |

**必需的请求头**（8 个）：

| Header | 说明 |
|---|---|
| `X-Auth-Type` | 固定 `1` |
| `X-Product-Key` | 产品标识符，与注册时一致 |
| `X-Device-Name` | 设备名，与注册时一致 |
| `X-Random-Num` | 随机数 |
| `X-Timestamp` | 时间戳，**单位：秒** |
| `X-Instance-Id` | 实例 ID，与注册时一致 |
| `X-Signature` | 见下 |
| `X-Hardware-Id` | 设备唯一标识，建议用 MAC |

签名算法：

```
content = "auth_type={auth_type}&device_name={device_name}&random_num={random_num}"
          "&product_key={product_key}&timestamp={timestamp}&instance_id={instance_id}"
signature = base64( HMAC-SHA256(key=device_secret, content) )
```

> ⚠️ **两个极易写错的差异**（官方专门加了「说明」）：
> ① **密钥不同**——注册用 `product_secret`，建连用 `device_secret`；
> ② **时间戳单位不同**——注册是**毫秒**，建连是**秒**。
> 时间戳过期窗口为 **1 分钟**（错误码 `30070217`）。

连接成功后，服务端下发 `session.created`，表示会话就绪。

**建连错误码**：`30070216`（时间戳非法）、`30070217`（时间戳过期）、
`30070301`（签名不合法）、`30070304`（请求头 X 缺失）、
`30070306`（设备不存在）、`30070307`（多设备共用同一密钥）。

### 1.4 步骤 3：双向通话

**客户端事件（上行）**

| 事件 | 用途 |
|---|---|
| `input_audio_buffer.append` | 追加 Base64 音频数据 |
| `input_audio_buffer.commit` | 提交输入缓冲（**仅非 VAD 模式**需要） |
| `input_audio_buffer.clear` | 清空缓冲区 |
| `conversation.item.create` | 添加文本消息 / 安抚语 / 函数调用结果 |
| `response.create` | 指示服务端生成响应 |
| `response.cancel` | 取消进行中的响应（**打断**） |

**服务端事件（下行）**

| 事件 | 用途 |
|---|---|
| `session.created` | 会话就绪，**携带音频格式与 VAD 配置** |
| `input_audio_buffer.speech_started` / `speech_stopped` | VAD 检测到说话开始 / 结束 |
| `input_audio_buffer.committed` / `cleared` | 缓冲提交 / 清除的响应 |
| `conversation.item.input_audio_transcription.completed` | **用户语音的最终识别文本**（字幕） |
| `response.created` | 响应开始生成 |
| `response.audio.delta` | **模型输出音频增量（Base64）→ 应立即解码播放** |
| `response.audio.done` | 音频生成完毕 |
| `response.audio_transcript.delta` / `.done` | 模型回复文本增量 / 最终（字幕） |
| `response.done` | 本轮全部内容生成完毕 |
| `conversation.item.created` | 触发端侧函数调用（`item.type = function_call`） |
| `response.function_call_arguments.done` | 完整函数参数 |
| `error` | 错误 |

**判停两种模式**：

- **VAD 模式（默认，推荐）**——服务端 `server_vad` 自动检测静音并截断
- **非 VAD 模式**——客户端主动发 `input_audio_buffer.commit`（适合「按住说话」）

**其他能力**：

- 实时字幕——监听 `response.audio_transcript.delta` 与
  `conversation.item.input_audio_transcription.completed`
- 主动播报——`conversation.item.create` 且 `item.content.type = input_tts`
- 文本提问——同上但 `item.content.type = input_text`
- 端侧 Function Calling 闭环——
  收 `conversation.item.created`(function_call) → 收 `response.function_call_arguments.done`
  （用 `call_id` 匹配参数）→ 执行 → 回 `conversation.item.create`
  且 `item.type = function_call_output`

### 1.5 音频格式

`session.created` 事件示例里给出的取值：

```json
{
  "type": "session.created",
  "session": {
    "model": "doubao",
    "modalities": ["text", "audio"],
    "input_audio_format": "pcm16",
    "output_audio_format": "pcm16",
    "turn_detection": { "type": "server_vad" },
    "temperature": 0.8
  }
}
```

> ✅ **采样率已确认（2026-09-22，通过火山技术支持获取）**：
>
> | 方向 | 采样率 | 位深 | 声道 | 依据 |
> |---|---|---|---|---|
> | **上行**（麦克风→火山 ASR） | **16000 Hz** | 16bit | mono | WebSocket 流式语音识别（大模型）固定 16kHz/16bit，不支持自定义 |
> | **下行**（火山 TTS→喇叭） | **24000 Hz** | 16bit | — | WebSocket 流式语音合成默认 24kHz（pcm/wav/mp3 格式） |
>
> ⚠️ 注意：以上是火山通用 WebSocket ASR/TTS 接口的规格。硬件对话智能体的 WebSocket 标准协议
> 内部可能有独立的处理链路，**建议在 P-A 建连后用真机验证**——若识别正常则采样率无误。
>
> 音频包发送频率建议 **100ms~200ms**；过小的音频包可能影响识别性能。

## 2. 为什么这条路线适合我们的板子

| 协议要求 | 我们的硬件 | 匹配度 |
|---|---|---|
| 上行输入音频 `pcm16` | 板载 PDM 麦克风**原生输出 16-bit PCM** | ★ 直接可用 |
| 下行输出音频 `pcm16` | 外接 MAX98357 **直接吃 I2S PCM** | ★ 直接可用 |
| 需要 Opus 编解码器 | **不需要** | ★ 省掉一整条编解码链，省 RAM 与 CPU |
| 需要本地 VAD | **不需要**（服务端 `server_vad`） | ★ 省算力 |
| 需要唤醒词 | 可选保留本地唤醒词 | ○ 二选一 |

**结论**：本项目的**音频链路已验证可用**（见 `项目进度.md`「硬件联调记录」），
而这条协议**恰好只要 PCM**——两边正好对上，改动集中在网络与协议层，不碰音频。

## 3. 路线 B 改动清单

### 3.1 保留不动（已实测验证）

- PDM 麦克风采集（DATA=41 / CLK=42）
- MAX98357 播放（BCLK=4 / LRC=5 / DIN=6）
- Wi-Fi 配网与连接
- 唤醒词引擎（若保留本地唤醒）

### 3.2 设备端需要新增或修改的部分

| # | 模块 | 要做的事 | 复用现有能力 |
|---|---|---|---|
| 1 | **设备注册** | HTTP POST 调 `DynamicRegister`，拿到 `Result.payload` | HTTP 客户端 |
| 2 | **AES-CBC 解密** | 用 `product_secret` 前 16 字节解出 `device_secret` | mbedTLS |
| 3 | **签名** | HMAC-SHA256 + Base64，**注册与建连两套拼串** | mbedTLS |
| 4 | **凭证持久化** | `device_secret` 存 NVS（**加密存储**），避免每次重启重注册 | NVS |
| 5 | **WebSocket 客户端** | `wss://ai-gateway.vei.volces.com/v1/realtime?bot=<bot_id>`，带全 8 个请求头 | TLS/WS 客户端 |
| 6 | **事件分发** | JSON 解析 + 事件路由（上行 6 类 / 下行 14 类） | cJSON |
| 7 | **音频上行** | PCM 分帧 → Base64 → `input_audio_buffer.append` | 现有采集 |
| 8 | **音频下行** | `response.audio.delta` → Base64 解码 → 写 I2S | 现有播放 |
| 9 | **状态机** | 连接 / 会话就绪 / 说话中 / 打断 映射到本地状态（含 LED 指示） | 现有状态机 |
| 10 | **配置注入** | `InstanceID` / `product_key` / `product_secret` / `bot_id` **从配置读取，不进代码** | 现有配置机制 |

### 3.3 服务端（本项目）——需要做一个决策

官方文档存在一处**内在张力**：

- 「准备工作」说 `product_secret` **切勿泄露或硬编码在客户端**；
- 「接入指引」又说 **设备端**调用 `DynamicRegister` 换取 `device_secret`。

两条同时满足的做法是：**注册动作由我们后端代做**，后端用 `product_secret` 调
`DynamicRegister`，把得到的 `device_secret` 安全下发给设备；设备只保存 `device_secret`。

| 方案 | 优点 | 代价 |
|---|---|---|
| **A. 设备直连**（`product_secret` 下发到设备） | 实现最快，设备独立工作 | ⚠️ 密钥落到设备上，**一机泄露即全线泄露**；且与官方「切勿泄露」的告诫冲突 |
| **B. 后端代注册**（推荐） | 密钥不出后端，符合官方告诫 | 设备首次上电需联网向后端取凭据；后端要新增一个下发接口 |

**★ 已定案（2026-09-20 用户确认）：选 B（后端代注册）。**
`product_secret` 不出后端；设备首次上电联网向后端换取 `device_secret` 并落 NVS 加密存储。
该接口纳入本项目的设备激活流程，与 P7 的 AI 配置链路合并考虑。

### 3.4 与 P7 架构的关系（需要重新界定）

设备直连火山后，**平台侧不再参与对话流量**。这带来一个必须明确的问题：

- 平台侧现有 P7 的 `Aibot*` OpenAPI 适配器，**定位要改成「管理面」**
  （建智能体、配人设、查用量），而不是「数据面」（转发音频）。
- 设备的**激活状态与用量统计**需要另找来源（注册记录 / 火山侧用量接口），
  否则「平台看板」会与实际使用脱节。

> 这一条**不属于本次改动清单**，但会影响 P9 看板的口径，**建议单独决策后再动**。

**关于采样率的取证过程**：

1. **2026-09-20（初轮）**：公网检索 + 本机全盘检索 + 浏览器实读官方文档五页正文
   → **「采样率 / Hz / 位宽 / 声道」零命中**；官方示例源码 → `I2S_SAMPLE_RATE = 16000`
2. **2026-09-22（确认轮）**：通过火山技术支持获取 WebSocket ASR/TTS 接口的完整采样率规格——
   - ASR（流式语音识别大模型）：固定 **16kHz / 16bit / mono**
   - TTS（流式语音合成）：pcm/wav/mp3 格式默认 **24kHz**，ogg_opus 格式 **48kHz**
   - RTC 场景（StartVoiceChat）：自定义 TTS 仅支持 **24kHz**

> **结论**：上行 **16 kHz**、下行 **24 kHz**，上下行不一致——这在同类产品中属于正常设计
> （ASR 需要 16kHz 匹配语音识别模型，TTS 用 24kHz 提供更好的音质）。
> 代码已按此配置：`AUDIO_INPUT_SAMPLE_RATE = 16000`，`AUDIO_OUTPUT_SAMPLE_RATE = 24000`。
